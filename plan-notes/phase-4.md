# Phase 4 — Progress UI — done (2026-07-20)

Full detail behind the one-line summary in PLAN.md.

- [x] Home page dashboard: per-operation mastery view (grid/heatmap of fact families), personal bests, streaks — `HomePage.vue` no longer shows the old per-section "pick a level 1-8" button grid directly; that flow moves down a level to `SectionPage.vue` (unchanged, still there for when you actually want to start a level). The home page now renders two `OperatorGroupPanel`s — "Addition & Subtraction" and "Multiplication & Division" — one per `OperatorGroup`, since mastery is tracked per group, not per operator, and showing four near-duplicate heatmaps (add's grid would be identical to subtract's) would just be confusing. Each panel has a `MasteryGrid` (new `src/components/MasteryGrid.vue`): an 8×8 grid over `MIN_FACTOR..MAX_FACTOR`, one cell per `factFamilyKey(group, a, b)`, colored by `stageBgClass(stage)` (new `src/dashboard.ts`, 6 buckets from `bg-base-300` at stage 0 to solid `bg-success` at stage 5) with a hover `title` showing the actual fact and stage. A `masterySummary()` helper (same file) drives the "N / 36 facts mastered (M in progress)" text next to each grid.
- [x] Milestone/badge display decoupled from raw difficulty — new pure `src/milestones.ts`: `highestClearedLevel(sectionId, maxLevel, getPersonalBest)` scans personal bests and returns the highest level with `percentCorrect >= LEVEL_CLEAR_THRESHOLD` (0.8), with no requirement that earlier levels were also cleared (levels were never sequentially gated to begin with). `OperatorGroupPanel.vue` shows a `🏅 Level N` badge per section once it has one. Also added a `best` field to the streak store (`src/stores/streak.ts`) — deliberately deferred in Phase 3 ("add it back if/when a real 'best streak' UI actually lands") — updated in `recordClean()`, surfaced at the top of the home page as "🔥 Best cheat-free streak: N" once non-zero.
- [x] JSON export/import of progress (local file, no server) — pure serialize/parse/apply logic in new `src/persistence-io.ts` (`buildProgressExport`/`parseProgressExport`/`applyProgressExport`, versioned `{ version: 1, ... }` shape covering all four stores), kept separate from the DOM glue in new `src/components/ProgressBackup.vue` (download via `Blob`+`<a download>`, import via a hidden file input's `change` event). Wired into the home page under a "Backup progress" panel. Invalid/unrelated JSON produces a friendly inline error instead of throwing into the console.
- [x] **Added after initial review, not in the original checklist:** a basic checksum defense against the obvious kid move of downloading the export, hand-editing `percentCorrect`/`stage` values to inflate them, and re-importing. New `src/checksum.ts` (`fnv1aHash`, a plain 32-bit FNV-1a hash — deliberately non-cryptographic) hashes the export payload's canonical `JSON.stringify` output; the hash rides along as a `checksum` field. `parseProgressExport()` recomputes it and rejects the import with "That file doesn't match its checksum — it looks like it was edited" if it doesn't match. Explicitly not real security (source is client-side and fully readable; a sufficiently motivated kid could read `checksum.ts` and forge a valid one) — it's a speed bump against casual text-editor tampering, matching this app's own "cheating has stakes" theme rather than being sold as tamper-proof.
- [x] Component tests for dashboard rendering against store fixtures — `src/components/MasteryGrid.test.ts` (cell count, per-family stage coloring against a seeded mastery store), `src/pages/HomePage.test.ts` (both group panels render, mastery summary reflects store fixtures, level badges appear/don't appear correctly, best-streak line only shows once set, export/import controls present), plus pure-logic unit tests `src/dashboard.test.ts`, `src/milestones.test.ts`, `src/persistence-io.test.ts`, and `src/stores/streak.test.ts`'s new `best`-tracking case.

## Bug found via manual browser verification, not caught by unit tests

`buildProgressExport()` originally used `structuredClone()` on the live Pinia store state to avoid aliasing the store's own objects in the exported snapshot. Every unit test passed, because they all called it with plain fixture objects. But real Pinia store state is a Vue reactive `Proxy`, and `structuredClone()` throws `"could not be cloned"` on those in a real browser — so clicking **Export progress** against the actual app threw an uncaught error and never triggered a download. Caught only by driving the real app end-to-end with a temporary Playwright script against the dev server — confirmed via console-error capture and a real `download` event.

First fix attempt swapped `structuredClone()` for a `JSON.parse(JSON.stringify(...))` round-trip, which worked but was an odd way to solve "can't clone a Proxy" — flagged in review. The actual right tool is Vue's `toRaw()`: it unwraps a reactive Proxy back to the plain object a store action originally assigned (Vue's reactivity wraps objects lazily on _read_, it never mutates what's stored, so the raw target under a Pinia store's state is always plain data), and `structuredClone(toRaw(x))` clones that directly. On a plain (non-reactive) object — e.g. in unit tests — `toRaw()` is a no-op, so the same code path works in both places. Added a regression test (`persistence-io.test.ts`) that wraps store fixtures in `reactive()` before calling `buildProgressExport()`, so a future regression on this exact issue fails a unit test instead of requiring a browser to catch.

Playwright is now a permanent devDependency (see PLAN.md library changes) instead of being added/removed per phase, since every phase ends up needing it for this kind of end-to-end check.

Re-verified in a real browser after both fixes: export fires a real download with a `checksum` field present, re-importing that exact file succeeds, and re-importing a copy with a hand-edited `percentCorrect` (the "cheat the cheat game" move that prompted the checksum feature) is rejected with the checksum-mismatch message.

## Design note: what stayed out of scope

Levels remain playable exactly as before (`SectionPage.vue` → `LevelLinks` → `LevelPage.vue`, level 1-8, difficulty fully adaptive since Phase 2). Phase 4 only changed what the _home_ page leads with — mastery-first instead of level-picker-first — per the "replaces 'pick a level number' flow" wording in the plan. Whether the level-number UI has any long-term place at all is still an open question in PLAN.md; not resolved here.
